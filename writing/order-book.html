Who trades first? Building a limit order book and matching engine in Java

Sebastian Alexander Escurra Carmelo

When you buy a share, your order does not go to another person. It goes to an order book: a list of everyone who wants to buy or sell, and at which price. A program called the matching engine decides who trades with whom, and at what price. The rules are simple to state, but a small mistake in them is unfair to someone.

I built a simulator of this in Java and tested it. This article explains the rules, how the code is organised, and how I checked that the code follows the rules.

1. The rules

An order says BUY or SELL, a limit price and a quantity. A buyer’s limit is the most they will pay, and a seller’s limit is the least they will accept. A BUY and a SELL can trade when the buy price is at least the sell price. The simulator follows five rules:

  • Price priority. The best price is served first: the highest buy and the lowest sell.
  • Time priority. At the same price, the order that arrived first is served first.
  • Trade price. The trade happens at the price of the order that was already waiting in the book. A buyer who offers 105 and meets a seller asking 101 pays 101.
  • Partial fills. The quantity traded is the smaller of the two quantities. A waiting order that is only partly filled keeps its place. If the new order is only partly filled, what is left is added to the book.
  • Sweeping. A new order keeps trading with the next best order, as long as the prices still match.

The simulator handles one instrument and only limit orders.

2. Four classes, each with one job

The code has four main classes (Figure 1). Order is one order: id, type, price, remaining quantity and arrival number. Trade is one execution: price, quantity and the ids of the buy and sell orders. OrderBook stores the waiting orders in two lists, buys and sells, always sorted with the best order first. MatchingEngine receives new orders, applies the rules and records the trades. Main runs five demonstration scenarios, and OrderBookTests runs the automated checks.

The split matters. The book only stores and sorts, and the engine decides. The two lists are private, so nothing outside the book can break the sorting. The book offers only the methods the engine needs, such as getBestBuy, removeBestSell and cancelOrder.

3. Time priority without comparing times

The book keeps each list sorted all the time. A new order is not added at the end and sorted later: it is inserted directly at its correct position, so the best order is always first. This is the code for a new buy:

int position = 0;
while (position < buyOrders.size()
        && buyOrders.get(position).getPrice() >= order.getPrice()) {
    position++;
}
buyOrders.add(position, order);

The detail is in >=. The loop skips every order whose price is better than or equal to the new one. So an order with the same price is placed behind the older ones. That gives time priority without comparing any times.

Who decides the arrival order? The engine does, not the user. It keeps a counter (1, 2, 3, …) and writes the number into each order when it arrives. A user cannot jump the queue by typing an older number.

4. A worked example

This is the second demo scenario. The book has three sell orders: id 2 and id 3 for 10 units at 100, and id 1 for 10 units at 101. Then a buy order for 25 units with a limit of 102 arrives (Figure 2).

The engine takes the best sell first. Orders 2 and 3 both ask 100, and order 2 arrived first, so it trades first: 10 units at 100. Then order 3 trades 10 units at 100. The buyer still wants 5 units, and the next best sell is order 1 at 101, which is still below the limit of 102. So 5 units trade at 101, and order 1 keeps its other 5 units in the book. The buyer offered 102 but never paid 102.

5. Rejecting bad orders

The engine checks every order before it touches the book. It rejects a type that is not exactly BUY or SELL, a price that is zero, negative or not a number, a quantity of zero or less, a missing order (null, meaning no order object at all), and an id that is already waiting in the book. It prints the reason, for example ORDER REJECTED (id=3): quantity must be positive. Checking at the entry point means the rest of the code can assume the order is valid.

6. How I checked it works

The test class runs 25 automated checks. Some test each rule with a small example: a full match, a partial fill of the waiting order, a partial fill of the new order, no match, time priority, price priority, trade price in both directions, a sweep across several price levels, cancelling and rejecting orders.

The last group is a random test. It sends 5,000 random orders, with a fixed seed so the run can be repeated, and after every single order it checks three properties that must always be true:

  • the book is never crossed: the best buy is below the best sell;
  • both lists are in price-time order;
  • no quantity is created or lost: what was submitted equals what was traded plus what is still waiting, on each side.

The random test also checks that some trades happened, because a random test where nothing trades would prove nothing. With the final code, all 25 checks pass.

I also checked that the tests are able to fail. Separately, I introduced three bugs on purpose, one at a time: wrong time priority, wrong trade price and wrong matching condition. The tests failed every time, and I removed the bugs afterwards.

7. Limits

  • Speed. Inserting, removing the best order, cancelling and checking for duplicate ids all take time proportional to the number of waiting orders. The book slows down as it grows. A faster design would keep one queue per price level in a sorted structure.
  • Prices are decimals. Prices are only compared here, never added, so it works. A real system would use whole numbers of cents to avoid rounding problems.
  • Only limit orders. There are no market orders and no order changes.
  • Duplicate ids are detected only among waiting orders, so an id that was already fully executed can be reused.
  • One instrument, one thread and no saved data.

What I take from this

The rules of an order book are easy to say and easy to get slightly wrong. The examples show that the rules work in the cases I thought of. The random test checks that three key properties keep holding in thousands of cases I did not choose by hand. That gives much more confidence, but it does not prove the code has no bugs.
